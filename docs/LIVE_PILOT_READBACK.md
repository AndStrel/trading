# Проверка боевого счёта — только чтение

`verify-live-pilot.yml` запускается вручную только с main, после deploy этой
же версии. Это подготовка существующего дневного счёта, не real-исполнение.
`LivePreflightClient` по-прежнему только читает и сам ничего не отправляет.
Отдельный боевой клиент ставит заявку только при режиме `live`, после
`/execution_arm LIVE` и `/approve ID CONFIRM`. Эта проверка режим не включает.

Команда оператора:

```sh
gh workflow run verify-live-pilot.yml --ref main
```

Workflow использует уже настроенный verified SSH и ту же production очередь,
что deploy. Сначала сверяются clean server SHA, существующий Compose контейнер,
его состояние и OCI revision; новые контейнеры не создаются. Затем внутри него
выполняется только `node dist/pilot-preflight.js`. Секреты остаются на сервере,
`.env` не выгружается и не копируется. Журнал исполнения не открывается.

Результаты:

- `account-checks-passed`: подтверждены текущие read-only проверки выбранного
  дневного счёта, Investor-тарифа, наличных, отсутствия позиций и активных
  поручений/стопов. Это не подтверждение стратегии или рабочего real adapter.
- `not-ready`: причины только фиксированными кодами; сырые ответы/ошибки,
  токены, account IDs и величина личного баланса не выводятся.
- Process exit 0 прежнего CLI не считается успехом: обязательны точные JSON
  booleans и `accountChecksPassed=true`. Новый verifier даёт exit 1 при отказе.

Во всех случаях `liveSubmissionAllowed=false`, `brokerWrites=false`. Даже при
успехе сохраняются отдельные gaps: стратегия не «допущена» этим workflow,
полный sandbox-цикл выбранной версии и точная денежная сверка на боевом счёте
не подтверждены. Наличие торгового токена само по себе заявку не включает.

Рабочий путь реальной заявки (отдельный модуль, не этот workflow):

1. В `.env` на машине запуска: `T_INVEST_EXECUTION_MODE=live`, отдельный
   `T_INVEST_LIVE_TOKEN` (или `T_INVEST_TRADING_TOKEN` с ролью `live`) и
   `T_INVEST_LIVE_ACCOUNT_ID`; read-only и sandbox-токены остаются другими.
2. Перезапуск контейнера (`npm run deploy` или production deploy).
3. В Telegram: `/status`, при необходимости `/pilot_check`, затем
   `/execution_arm LIVE` и `/approve ID CONFIRM` по одной карточке.
4. После покупки сервис ставит один стоп-лимит; при неопределённости —
   `/reconcile ID`, не повторный `/approve`. `/kill` снова запрещает новые
   отправки; уже открытую позицию не закрывает.

Сейчас live preflight подтверждает только Investor; Trader/условные 0,03% —
отдельные research-сценарии и не поддерживаемый производственный floor.
Смена тарифа требует отдельной проверки фактических расходов, не замены числа
ради прохода backtest.

45 секунд ограничивают внешний verifier. Timeout Docker-клиента не гарантирует
немедленное завершение Node/HTTP-чтения внутри существующего контейнера:
оно может дойти до собственного таймаута. Это только READ, не повтор заявки.
Никакого автоматического retry/признания счёта готовым после timeout нет.

Приёмка: synthetic unit tests без сети/Docker проверяют несовпадение SHA,
небезопасный/сменившийся runtime, неверный JSON, exit 0 при false readiness,
пределы пилота, неизвестные blocker strings, timeout и отсутствие секретов
во всех публичных ответах. Они не заменяют фактический read-back с main.
