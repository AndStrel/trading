# Выход по неизменной цели и восстановление sandbox-защиты

Этот этап реализует программный протокол, не подтверждает прибыльность стратегии
или готовность реального исполнения. Все проверки ниже локальные и синтетические.
Реальные счета, секреты и действующий серверный env этим изменением не меняются.

## Включение и неизменяемый план

`T_INVEST_SANDBOX_TARGET_EXIT_ENABLED=false` по умолчанию. Для работы нужны
`mode=sandbox`, отдельный sandbox-токен/подготовленный счёт, `prepare=true`,
native protection, loss guard и session close. Ни этот флаг, ни выбор алгоритма
не разрешают live-заявки и не создают/пополняют счёт.

Автоматическая попытка цели распространяется только на НОВЫЙ одобренный
`intraday-scanner` сценарий известного алгоритма версии `1`, в котором при
создании зафиксированы `sandboxTargetExitPolicy.version=1`, `enabled=true`,
исходные комиссии/проскальзывание и метаданные инструмента. Старые/manual/technical
сценарии не становятся target-сценариями при изменении env, стратегии или watchlist.
Покупка по-прежнему требует отдельного подтверждения оператора.

Перед отменой защиты сверяются фактические terminal BUY-исполнения и известные
комиссии. Расчёт в целых nanoruble требует положительную модельную прибыль и
отношение чистой цели к риску с расходами не ниже 2. Комиссия каждой стороны —
большее фактической и модельной комиссии; модельный минимум пока 0,3% за сторону.
Дополнительно резервируется объявленное проскальзывание обеих сторон. Расходы
округляются вверх до копейки; цена остаётся точной по шагу инструмента.

Достаточная свежая BID-глубина для ВСЕЙ позиции должна быть не хуже исходного
`targetPrice`. Записывается единственный durable target intent, только его
победитель CAS отменяет известный стоп. После точного `CANCELED` без child вновь
читаются BUY/комиссии, позиции, ордера, инструмент, статус торгов и BID-глубина.
Ревизия журнала не должна измениться за время этой последней сверки. FOK SELL
имеет предел ровно исходный target, а не более высокую показанную цену BID.
После claim SELL — максимум один POST; timeout/not-found не разрешают повтор.

После 18:30 МСК приоритет имеет отдельно описанный session exit по текущей
исполнимой BID-цене; он не обещает прибыль. Показатель `targetAchieved` означает
исполнения не ниже исходной цели и положительный консервативный модельный net,
а не итоговое отношение 2:1 после любых будущих комиссий и не допуск стратегии.
Фактический виртуальный PnL и модельный net различны. Даже полная продажа требует
свежего flat/account read-back; это не доказательство денежного cash-flow от
исходного баланса, реального исполнения, налогов или оплаты обслуживания счёта.

## Безопасное восстановление

Восстановление допускается только для этого opt-in протокола:

- цель стала невалидной после подтверждённой отмены, но SELL ещё НЕ claimed;
- точная SELL по сохранённому UUID/broker ID terminal `REJECTED`/`CANCELLED`,
  исполнено ровно ноль, stages пусты, gross нулевой.

Частичное исполнение, NEW, отсутствие заявки, timeout и неизвестный результат
запрещают новый стоп/SELL. Пропущенные комиссии не превращаются в ноль, но не
мешают восстановить защиту после физически доказанного нулевого SELL.

Нужно заново подтвердить исходный CANCELED стоп без child, полный незаблокированный
остаток покупки, отсутствие активных ордеров и посторонних стопов. SQLite CAS
атомарно запрещает старому actor отправить SELL, архивирует исходные identities
и создаёт поколение native stop `g+1`: НОВЫЙ UUID, прежний stop/limit, фактическое
количество BUY. Только победитель отправляет один новый stop POST. Лишь точный
ACK и свежие ACTIVE/позиции/ордера означают восстановленную защиту. При новом
EXECUTED сверяется известный native child, отдельный SELL не отправляется.

Максимум один target attempt и один последующий session attempt на всю позицию.
После восстановленного отказа session собственная продажа больше не повторяется:
native stop продолжает сопровождение, kill остаётся включённым, дневное закрытие
не считается выполненным. Повторные monitor/restart не отправляют новый stop.
Старый worker не может записать старый CANCELED поверх ACTIVE поколения `g+1`:
каждый observe/ACK/exit привязан к captured generation/request/broker identities.

Архив zero-SELL хранится отдельно от final exit evidence. Поздние комиссии
перечитываются только по прежнему точному UUID и изменяют результат/дневной
loss guard ОДИН раз. Unknown/regressed/противоречащие fees делают результат и
loss proof неполными, не отменяя новый защитный стоп.

## Известные границы и откат

Отмена старого и постановка нового стопа НЕ атомарны у брокера. Между ними
защиты может не быть. При неизвестном ACK нового stop POST текущий клиент не
имеет подтверждённого lookup по client UUID: похожая цена/время не доказывают
identity, второй POST запрещён. Это НЕ успешное восстановление; kill/личное
предупреждение и проверка оператором необходимы. Stop-limit может не исполниться
при гэпе, внешние изменения счёта между read-back остаются риском.

До любых изменений версии: сохранить приватную резервную копию SQLite. Legacy
g0 записи совместимы, но ПОСЛЕ появления g1 нельзя откатывать к старому коду,
который не проверяет generation или не учитывает архив расходов. Сначала закрыть
и сверить flat-состояние либо сохранить новый модуль сопровождения. Не удалять
журнал/volume и не считать выключение флага закрытием позиции.

`/reconcile` и startup recovery по-прежнему READ ONLY; они не продвигают
cancel/submit/restore. Защитный worker отдельно может продвигать заранее
одобренный sandbox-протокол, но никогда автоматически не снимает kill/резерв.
