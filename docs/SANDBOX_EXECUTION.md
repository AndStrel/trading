# Sandbox-исполнение заявок

## Что автоматизировано

Telegram-сервис сам запускает intraday-сканер при старте контейнера. Сканер сразу делает первый проход, затем запускается через каждые пять минут на границе интервала. Отдельный cron и расписание GitHub Actions не нужны: Docker Compose использует `restart: unless-stopped`, поэтому процесс поднимется после перезапуска VPS.

Когда сканер сохраняет новый `candidate`, executor автоматически создаёт локальное поручение `pending` с неизменяемым UUID. На этом шаге запроса на выставление брокерской заявки ещё нет. Авторизованный оператор получает карточку и нажимает `Подтвердить sandbox` или `Отклонить`. Текстовые команды остаются резервным вариантом:

```text
/approve ID CONFIRM
/reject ID
```

Только явное нажатие кнопки или точная команда подтверждения запускает повторную проверку рынка и отправку лимитной FOK-заявки в T-Invest Sandbox.

## Состояния поручения

| Состояние | Значение | Допустимое действие |
|---|---|---|
| `pending` | Кандидат сохранён, брокерский запрос не выполнялся | подтвердить или отклонить |
| `rejected` | Оператор отказался от сделки | действий нет |
| `submitting` | Запрос отправляется или его сетевой результат неизвестен | сверить состояние, не повторять POST |
| `accepted` | Sandbox принял запрос | повторная отправка запрещена |
| `failed` | Sandbox однозначно отклонил запрос | повторная отправка запрещена |

При сетевом таймауте нельзя считать, что заявки нет. Запись остаётся `submitting`,
а `/reconcile ID` читает `GetSandboxOrderState` по сохранённому UUID с
`ORDER_ID_TYPE_REQUEST`. Повтор `/approve ID CONFIRM` для `submitting` также
выполняет только это чтение, не POST. Работает после рестарта, при kill и истечении
кандидата. При старте настроенного sandbox выполняется ограниченная сверка первых
20 unresolved/accepted записей; `morePending` явно сообщает неполную выборку.
Проверяются UUID, UID инструмента, направление, тип, RUB, количество лотов,
согласованность статуса и сумма отдельных сделок. Пропущенное число исполненных
лотов не считается нулём. Цены умножаются на лоты и лотность в целых nanoruble.
Отсутствующие комиссии остаются неизвестными, а не нулевыми.
Снижение ранее известного исполнения, смена сделок/цены/биржевого ID или регресс
комиссий отклоняются транзакционно. Только подтверждённый terminal с нулевым
исполнением снимает резерв; частичное исполнение сохраняет возможную позицию.
Legacy accepted без сохранённого fill count не освобождается по нулевому ответу.
HTTP-ошибка или «не найдено» не доказывает отсутствие заявки.
Executor использует заданный `T_INVEST_TRANSPORT`, в том числе `system-curl`,
с проверкой TLS. Общим с read-only клиентом остаётся только низкоуровневый
однократный транспорт, не объект клиента или токен. Нет retry или fallback
после сетевого/HTTP-сбоя. Рабочий доступ к котировкам не доказывает доступ sandbox.

## Защитные ограничения

- отдельный `T_INVEST_TRADING_TOKEN`, который не передаётся MCP и сканеру;
- торговые записи только в `SandboxService`: `PostSandboxOrder`, опциональный `PostSandboxStopOrder` и, при отдельно включённом выходе из сессии, `CancelSandboxStopOrder` для собственного подтверждённого стопа; live-endpoint в клиенте отсутствует;
- только long, лимитная заявка, `TIME_IN_FORCE_FILL_OR_KILL`, `confirmMarginTrade=false`;
- один заранее рассчитанный размер и цена из карточки;
- повторная проверка возраста кандидата, торгового статуса, bid/ask, спреда, отклонения цены и ликвидности;
- дневной лимит заявок и суммы расчётного риска по московскому календарному дню;
- в дневном пилоте максимум одна unresolved-заявка/возможная позиция; атомарный claim
  не допускает повторную отправку даже из двух процессов с общим SQLite;
- kill switch включён по умолчанию и сохраняется после рестарта;
- состояния, сделки и события записываются в закрытый SQLite без токенов; ID
  sandbox-счёта остаётся только в приватном runtime state, не в git или публичных ответах.

`/kill` запрещает только новые отправки. Он не закрывает уже исполненную sandbox-позицию и не отменяет принятую брокером заявку.

## Настройка

Сохраните на сервере два разных токена:

```dotenv
T_INVEST_TOKEN=токен-только-для-чтения
T_INVEST_BASE_URL=https://invest-public-api.tbank.ru/rest
T_INVEST_EXECUTION_MODE=sandbox
T_INVEST_TRADING_TOKEN=отдельный-токен-с-правом-торговли
T_INVEST_SANDBOX_ACCOUNT_ID=
T_INVEST_SANDBOX_INITIAL_BALANCE_RUB=1000
T_INVEST_EXECUTION_MAX_ORDERS_PER_DAY=3
T_INVEST_EXECUTION_MAX_DAILY_RISK_RUB=60
T_INVEST_EXECUTION_CANDIDATE_MAX_AGE_MINUTES=10
T_INVEST_SANDBOX_PROTECTION_ENABLED=false
```

После deploy выполните в Telegram:

`T_INVEST_BASE_URL` относится к read-only клиенту котировок и реальных данных.
Sandbox-клиент использует отдельный фиксированный
`https://sandbox-invest-public-api.tbank.ru/rest`; он не наследует этот env-параметр.
Не переключайте основной адрес на песочницу и не меняйте режим исполнения ради
создания или пополнения счёта.

1. `/execution` — режим `sandbox`, токен задан, kill switch включён.
2. После отдельной подтверждённой подготовки — `/execution_arm SANDBOX`. Команда только читает данные, ничего не создаёт и не пополняет. Kill switch выключается только после всех проверок.
3. `/orders` — до появления кандидатов список пуст.
4. После карточки — `/approve ID CONFIRM` либо `/reject ID`.
5. `/orders` и `/reconcile ID` — проверить итоговый статус и исполнения.
6. `/kill` — снова запретить отправки.

Для начальной активации требуется приватный `execution.sandbox_bootstrap_v1`:
версия 1, dedicated sandbox endpoint, UUIDv4 nonce, связанное имя
`daily-pilot-<nonce>`, фаза `ready` и подтверждённый ID, совпадающий с
`execution.sandbox_account_id` и настроенным ID, если он задан. Запись создаётся
отдельной контролируемой подготовкой; не редактируйте фазу вручную для обхода
неопределённого результата. Этот runbook не разрешает новую попытку создания
или пополнения после потерянного ответа.

Активация требует ровно одного принадлежащего подготовке счёта, явно пустых
позиций/заявок/стопов, отсутствия заблокированных средств и RUB-остатка, равного
начальному лимиту. Проверки должны уложиться в 30 секунд. Принятые или
неопределённые поручения требуют отдельной сверки, а не повторной активации.
Любая ошибка оставляет kill включённым; средства автоматически не добавляются,
в том числе для компенсации убытков. Параллельный kill (даже повторный `true`)
и изменения подготовки отменяют активацию. Новые подтверждения повторно
проверяют поколение kill и снимок подготовки атомарно перед резервированием.
Сверка ранее отправленной неопределённой заявки остаётся read-only и доступна
при kill или старой/неопределённой подготовке; новый POST она не делает.

`npm run smoke:sandbox-arming` проверяет собранный runtime на синтетическом
SQLite и подставных клиентах: неизвестная подготовка сохраняется, активация
готового счёта делает только чтение, параллельный kill остаётся включённым.
Скрипт не загружает окружение, реальные токены или серверный журнал. CI запускает
его внутри контейнера без сети, с read-only rootfs и временным `/tmp`; эта
проверка не подтверждает связь с брокером, sandbox round trip или live-готовность.

## Опциональный нативный стоп в песочнице

`T_INVEST_SANDBOX_PROTECTION_ENABLED=false` по умолчанию. Разработка и локальные
тесты не являются приёмкой настоящего брокера. На сервере флаг остаётся выключен:
проверка полного цикла на реальном sandbox ещё не выполнена.

При отдельном включении флага в режиме `sandbox` с изолированным токеном и
профилем дневного пилота до BUY требуется подтверждённый пустой счёт: только RUB,
достаточно доступных денег с расходами, нет позиций, активных ордеров и стопов.
После явно одобренной покупки читаются terminal-исполнения и фактический остаток.
Только для целиком подтверждённого объёма (включая terminal partial fill)
создаётся SELL STOP_LIMIT без плеча; цена лимита равна плановой стоп-цене.
Стоп не снимается автоматически в конце дня: GTC сохраняет его при рестарте.
Закрытие внутри дня и отмена без гонки с дочерней заявкой ещё не реализованы.

UUID и intent сохраняются атомарно **до** единственного POST. Известный broker
stop ID читается и проверяется после рестарта. При потерянном ответе POST повторять
нельзя: intent остаётся неизвестным, новые входы блокируются, риск не освобождается.
Стоп из общего списка не присваивается по похожей цене/объёму: в `GetStopOrders`
нет исходного request UUID. Необходима отдельная ручная сверка с брокером.
Конкурирующие процессы допускают максимум один POST; второй процесс может
консервативно включить kill, если первый ещё не сохранил acknowledgement.

Опциональный последовательный worker проверяет защиту каждые 30 секунд после
завершения предыдущего прохода; он ждёт настройки счёта, не создаёт и не пополняет
его. Worker и отправка одной заявки внутри процесса разделяют один запрос защиты.
После kill защитные действия для уже одобренной sandbox-покупки разрешены,
но kill не снимается автоматически. `/reconcile` и startup recovery остаются
**только чтением**, стопы не выставляют. Несовпадение позиции/стопа блокирует входы.

`STOP_ORDER_STATUS_EXECUTED` означает создание дочерней заявки, а не доказанную
продажу: её ID сохраняется, `positionClosed=false`, резерв остаётся. Нельзя
объявлять чистую прибыль, фактический дневной убыток или пустой счёт по этому
статусу. Стоп-лимит может не исполниться при гэпе; 20 ₽ не гарантируются.

Контракты: [stoporders.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/stoporders.proto),
[SandboxService](https://developer.tbank.ru/invest/api/sandbox-service-post-sandbox-stop-order).

## Проверка дочерней продажи и результата

Нативный stop `EXECUTED` по-прежнему не равен проданной позиции. Опциональный
sandbox-worker после этого статуса читает дочерний `GetSandboxOrderState` по
сохранённому `exchangeOrderId` с `ORDER_ID_TYPE_EXCHANGE`, а не UUID покупки.
Разрешены только совпадающие ID/UID, SELL LIMIT в RUB и точный объём фактической
terminal-покупки. Проверяются отдельные сделки, отсутствие дублей, их хронология
после покупки и монотонность ранее сохранённых исполнений/комиссий.

Это **только чтение**: клиент учёта продаж не умеет выставлять/отменять заявки,
создавать/пополнять счёт. `/reconcile ID` и startup recovery также читают продажу,
когда сохранённый нативный стоп уже связан с известным дочерним ордером.
Worker не делает второй SELL и не создаёт дополнительный стоп при частичной
продаже: новые входы блокируются, остаток и резерв сохраняются.

`sandbox_exit_evidence` хранит приватные фактические стадии продажи. Полная
продажа требует terminal-статуса с объёмом, равным подтверждённой покупке.
После неё отдельно проверяется пустой RUB-счёт, отсутствие блокировок, активных
ордеров и стопов; второй read-back должен по-прежнему связывать наш стоп с тем
же дочерним ID. Если эта проверка неудачна, проданные лоты сохраняются, но новый
флаг пустого счёта не выставляется (предыдущий очищается).

Итог пары = фактическая выручка − фактическая стоимость покупки − сообщённые
комиссии обеих сторон. Расчёт целочисленный, в nanoruble. Модельное проскальзывание
повторно не вычитается: эффект цены уже есть в фактических исполнениях. При
частичной продаже или отсутствующих комиссиях PnL неизвестен. Увеличенные поздние
комиссии пересчитывают результат, а не замораживают выгодный старый PnL. Возвращаемый
итог использует текущую покупку внутри финальной транзакции журнала.

Панель показывает только отдельные **sandbox**-результаты, дату последней сверки,
проданные/оставшиеся лоты и известный результат после комиссий. Не выдаёт ID счёта,
брокерских ордеров или сырые сделки. Это до налогов и иных расходов счёта, не
фактический live PnL и не оценка доходности реальной стратегии: виртуальные цены
и комиссии не заменяют прежние Investor-floor/stress/admission проверки.
Сведения о пустом счёте относятся к указанной сверке, не гарантируют его текущее
состояние при внешних действиях. Прибыль округляется вниз, убыток вверх по модулю
до копейки только для показа; точные nanoruble остаются источником истины.

Даже полный sandbox-результат **не освобождает** резерв и не снимает kill.
Контроль sandbox-убытков и опциональный выход из сессии описаны ниже. Освобождение резервов и
broker round-trip acceptance ещё не завершены; `lossMonitorReady=false` относится к live, live
PnL остаётся неизвестным, реальное исполнение выключено. При локальном тестировании
и установке этого этапа брокерские заявки не отправляются, флаг защиты остаётся
`false`. Основание полей/лотности: [orders.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/orders.proto),
остатков: [operations.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/operations.proto).

## Приёмка перед следующим этапом

### Опциональный выход из sandbox-позиции до конца дня

`T_INVEST_SANDBOX_SESSION_CLOSE_ENABLED=false` по умолчанию и при установке на
сервер. Этот контур не разрешает live, не создаёт/пополняет счёт и не открывает
новую позицию. Для его работы нужны изолированный sandbox-токен/счёт, нативная
защита, loss guard, одобренный дневной профиль и подтверждённая человеком покупка.

Консервативное окно пилота: входы по будням **10:05 ≤ время < 18:00 МСК**,
попытка закрытия с **18:30 МСК**. Это не биржевой календарь: статус
NORMAL_TRADING, разрешение API/лимитной заявки и свежая BID-глубина проверяются
отдельно. Вход повторно проверяется по реальному времени после preflight.
Неизвестная/двойная запись инструмента в watchlist, другая лотность или
неподтверждённый шаг цены запрещают вход до каких-либо заявок. Перед входом и
выходом read-only `GetInstrumentBy` дополнительно сверяет UID, лотность, шаг цены,
RUB и тип share, разрешение API/продажи (перед входом также покупки). Текущий
контур не поддерживает ETF, облигации или фьючерсы: они блокируются **до BUY**,
а не после обнаружения неподдерживаемой позиции. Более поздний
день не сбрасывает необходимость закрыть перенесённый остаток.

Для выхода нужна полная terminal-покупка с известной комиссией и единственный
остаток этого сценария; неизвестные позиции, активные ордера/стопы, блокировки,
недостаток BID-объёма или закрытые торги не считаются разрешением на продажу.
Сначала фиксируется уникальное намерение `sandbox_session_exit_intents`, затем
**один** `CancelSandboxStopOrder` только для нашего точно известного стопа.
HTTP ACK не равен отменённому стопу: статус и позиции считываются заново.
Если стоп уже `EXECUTED`, отдельный SELL не отправляется — сверяется только
известная дочерняя заявка. Стоп CANCELED без нашего durable-намерения не усваивается.

После подтверждённого CANCELED, неизменного остатка и отсутствия ордеров повторно
считываются рынок/позиции, проверяется свежесть всего объёма и точный шаг цены.
Единственная FOK SELL в sandbox задаётся по худшему BID, нужному для всего объёма,
целыми nanoruble, `confirmMarginTrade=false`. Claim SELL атомарно привязан к
ревизии исполнений/комиссий/стопов. Другой процесс не может повторить отправку.
Поздняя комиссия между сверкой и claim инвалидирует допуск.

После HTTP timeout, неизвестной отмены или рестарта Cancel/SELL не повторяются.
Подтверждённая последующим чтением отмена может допустить **первый** SELL, если
он ещё не был claimed. После claim SELL даже отсутствие ответа/ордера в раннем
lookup — не разрешение отправить снова: запрос ищется только по тому же UUID.
Startup recovery и `/reconcile` только читают; не продвигают cancel/submit этапы.
SELL проверяется по UUID, UID, направлению, объёму, известному exchange ID и
исполнениям не раньше его claim. Полная продажа требует отдельной flat-сверки,
отсутствия активных ордеров/стопов и подтверждения прежнего CANCELED стопа.
Поздние комиссии учитываются в общем sandbox-результате и дневном loss guard.

Kill остаётся включённым, резерв автоматически **не** освобождается, PnL live
не появляется. Нулевая/частичная FOK, недостающие комиссии или противоречие
снимков сохраняют неподтверждённый результат; второй SELL не делается. **Между
отменой стопа и подтверждённой продажей, а также при отклонённой FOK, позиция
может остаться без активного стопа.** Это требует контроля оператора; автоматический
fallback/re-arm ещё не реализован. Снимки не атомарны, внешние действия остаются
риском. Контур не гарантирует продажу, её цену, максимум убытка или отсутствие
переноса на следующий день. Полный брокерский sandbox-цикл и сценарии отказа
должны быть реально приняты до любого live-включения.

При разработке и установке этапа используются только локальные заглушки,
брокерские Cancel/SELL не вызываются, все торговые флаги остаются выключенными.
Контракты: [sandbox.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/sandbox.proto),
[stoporders.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/stoporders.proto),
[orders.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/orders.proto).

### Личное предупреждение оператора sandbox

При включённой нативной sandbox-защите существующий монитор проверяет защиту,
закрытие и (если включён) loss guard каждые 30 секунд. Неопределённая защита,
незавершённая сверка, переполнение ограниченной выборки или предел потерь
атомарно сохраняют инцидент и включают kill. Ошибки не включают новые входы.
Завершившаяся без ошибок проверка завершает текущий инцидент, но **не** снимает
kill, не освобождает риск и не подтверждает готовность LIVE.

Предупреждение с кнопкой «Панель» отправляется только положительным private ID
из `TELEGRAM_ALLOWED_CHAT_IDS`; группы и произвольные получатели исключены.
Текст содержит только категорию проблемы, время сверки и просьбу проверить
счёт/ордера/стопы. В нём и в журнале процесса нет токенов, брокерских ID, объёма
позиций или личных данных. Private ID и внутренние ключи доставки остаются
только в закрытом SQLite. До 50 получателей одного инцидента; отсутствие
разрешённого личного получателя или сбой доставки отражаются безопасными
флагом/счётчиками, а не скрываются успешным результатом.

SQLite claim доставки допускает одного отправителя на получателя/инцидент.
Успешный ответ Telegram сохраняется, поэтому повторный тик и рестарт не
повторяют подтверждённое предупреждение. Неизвестный ответ/авария между
отправкой и ACK могут дать повтор **не раньше пяти минут**, только после свежей
проверки текущего активного инцидента (не старше 60 секунд). Это at-least-once,
не exactly-once: дубли после неизвестного ответа возможны. Старый ACK не может
подтвердить попытку с новым lease. История инцидентов и последнее состояние
доставки каждому получателю сохраняются; полный архив всех повторных попыток
не ведётся.
Один непрерывный инцидент не создаёт сообщения на каждом изменении категории;
после успешной проверки новый инцидент получает отдельное предупреждение.

Предупреждение — **не автоматическое восстановление защиты** и не доказательство
отсутствия позиции. Отправка уведомления не вызывает broker Cancel/SELL/STOP,
не повторяет заявку и не снимает kill. Если процесс/SQLite/Telegram недоступен,
доставка не гарантируется; необходим внешний эксплуатационный контроль.
При выключенном исполнении или флаге нативной защиты монитор уведомлений
ничего не читает у брокера, не создаёт инциденты и не отправляет сообщения.
Поля метаданных: [instruments.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/instruments.proto).

### Опциональная read-only защита по sandbox-убыткам

`T_INVEST_SANDBOX_LOSS_GUARD_ENABLED=false` по умолчанию. На сервере флаг не
включается этим обновлением. Для работы нужны sandbox-профиль, изолированный
токен, включённая нативная защита и отдельный выбранный sandbox-счёт. Пределы
остаются 20 ₽ на пару и 60 ₽ в день; флаг не разрешает live и не создаёт счёт.

Сверка читает известные покупки, стопы, дочерние продажи, комиссии, текущие
позиции и заявки. Любая неизвестная позиция, активная заявка/стоп, пропавшая
защита, незавершённая покупка, недостающая комиссия или переполнение ограниченного
журнала (50 строк) означает **неизвестный** убыток, а не ноль: новые входы
блокируются durable kill. Флаг никогда автоматически не снимает kill.

Завершённые пары учитываются по фактическому результату и московскому дню
последнего исполнения SELL. Прибыльные пары не пополняют лимит убытков. Открытый
остаток оценивается целиком по свежему BID (`orderbookTs`, не старше 15 секунд,
не более 1 секунды в будущем), с достаточным объёмом по уровням и разрешёнными
торгами. Оригинальная стоимость покупки не сбрасывается на новый день. К
фактическим комиссиям исполненной части добавляются только прогнозные комиссия
(не ниже 0.003) и проскальзывание оставшейся продажи, округлённые вверх до копейки.
Уже состоявшаяся продажа повторно модельными расходами не облагается. После
частичного terminal SELL нет подтверждённой защиты остатка — входы закрыты.

Достижение 20 ₽ убытка по паре или суммы 60 ₽ по дню включает kill. При новом
входе также требуется, чтобы убыток + расчётный риск заявки укладывались в 60 ₽.
Допуск имеет срок 30 секунд и привязан к счёту, московской дате и ревизии
исполнений/комиссий/стопов. Проверка допуска, kill и резервирование выполняются
одной SQLite-транзакцией. Новая комиссия, исполнение или параллельное подтверждение
инвалидируют старый допуск. Дольше 30 секунд вся сверка не считается свежей.
Перед подтверждением повторно проверяются рынок и возраст кандидата; календарный
бюджет выбирается по реальному времени подтверждения, не по началу сверки.

Панель отдельно показывает статус sandbox-контроля и суммы только при свежей
полной оценке соответствующего счёта/ревизии. Не выводит ID счёта, доказательства,
ордера, токены или сырые сделки. Контроль не выполняет SELL/Cancel, не освобождает
резерв и не гарантирует цену будущей продажи или максимальный убыток. Снимки
брокера не атомарны, внешние действия между запросами остаются риском. Стоп-лимит
может не исполниться. Это не монитор фактического live-убытка, не доказанная
стратегия и не пройденный брокерский полный цикл. Источник лотности и времени
стакана: [marketdata.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/marketdata.proto).

Песочницу нельзя считать проверенной по одной успешной заявке. До live-разработки нужно накопить достаточную выборку, проверить отсутствие дублей после рестартов и таймаутов, сверить статусы с брокером, а также реализовать автоматические защитные выходы и фактический дневной PnL/лимит убытка.

Контракт полей и idempotency UUID взят из официального [orders.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/orders.proto), sandbox-маршруты — из [sandbox.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/sandbox.proto). Общие ограничения алгоритмической торговли описаны в [официальной документации T-Invest API](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/algorithmic_trading.md).
# Дневной пилот: подготовка, не live-исполнение

Одобренные пределы: капитал 1 000 ₽ включая расходы входа, расчётный риск
20 ₽ на сделку, суммарный расчётный риск 60 ₽ в день. Дополнительно предусмотрен
порог фактического дневного убытка 60 ₽; его **live-монитор ещё не реализован**,
опциональный sandbox-контроль описан выше.
Плечо и шорты запрещены; недельный счёт нельзя использовать как дневной.

`T_INVEST_LIVE_PILOT_PREPARE=true` включён по умолчанию. Этот профиль ограничивает
старые `INTRADAY_*` настройки, резервирует деньги на расходы входа и не допускает
комиссию ниже 0.003 на сторону для акций на тарифе «Инвестор». Большие значения
расходов сохраняются. Новые `T_INVEST_LIVE_*` лимиты допускают только уменьшение;
расширение одобренных пределов требует нового решения пользователя и изменения
политики. Исторические сценарии перепроверяются перед sandbox-очередью/отправкой:
их дешёвый snapshot не считается источником истины для расходов.

`/pilot` показывает лимиты, `/pilot_check` выполняет только чтение отдельного
счёта. Отдельные `T_INVEST_LIVE_TOKEN` и `T_INVEST_LIVE_ACCOUNT_ID` задаются только
на машине исполнения, не в git и не в чате. Live-токен не совпадает с read-only
или sandbox-токеном. Для чтения используется отдельный клиент без методов записи;
проверка TLS включена, production endpoint закреплён, перенаправления запрещены.
Команда `npm run preflight:pilot` выдаёт безопасный диагностический отчёт без ID,
секретов и реальных позиций. Даже прошедшая проверка счёта не разрешает заявку.

`assessLivePilotRisk` считает деньги целыми nanoruble и округляет расходы вверх
до копейки; проверяет расходы обеих сторон, целые лоты, доступные деньги,
плановый дневной бюджет и предоставленный фактический убыток. Это чистая функция,
**не** механизм резервирования риска, сверки и контроля убытка реального счёта.
Sandbox-резервирование
дневного бюджета выполняется атомарно с подтверждением; дата первого подтверждения
не изменяется при позднем ответе, HTTP 5xx не освобождает резерв. Отменённая заявка
с частичным исполнением также сохраняет резерв.
Для будущего live-исполнителя необходимы атомарное резервирование, один открытый
инструмент, отдельное подтверждение LIVE, broker-native stop, восстановление
неопределённых отправок по тому же UUID, учёт фактических комиссий/убытков,
закрытие внутри торговой сессии и проверка полного цикла в настоящей sandbox.
Пока этого нет, `T_INVEST_EXECUTION_MODE=live` не принимается. Не выдавать локальные
mock-тесты за брокерскую sandbox-приёмку. Стоп не гарантирует предел убытка при гэпе.
