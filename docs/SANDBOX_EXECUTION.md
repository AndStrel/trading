# Sandbox-исполнение заявок

## Что автоматизировано

Telegram-сервис сам запускает intraday-сканер при старте контейнера. Сканер сразу делает первый проход, затем запускается через каждые пять минут на границе интервала. Отдельный cron и расписание GitHub Actions не нужны: Docker Compose использует `restart: unless-stopped`, поэтому процесс поднимется после перезапуска VPS.

Когда сканер сохраняет новый `candidate`, executor автоматически создаёт локальное поручение `pending` с неизменяемым UUID. На этом шаге запроса на выставление брокерской заявки ещё нет. Авторизованный оператор получает карточку и нажимает `Подтвердить sandbox` или `Отклонить`. Текстовые команды остаются резервным вариантом:

```text
/approve ID CONFIRM
/reject ID
```

Только явное нажатие кнопки или точная команда подтверждения запускает повторную проверку рынка и отправку лимитной FOK-заявки в T-Invest Sandbox.

## Состояния поручения

| Состояние | Значение | Допустимое действие |
|---|---|---|
| `pending` | Кандидат сохранён, брокерский запрос не выполнялся | подтвердить или отклонить |
| `rejected` | Оператор отказался от сделки | действий нет |
| `submitting` | Запрос отправляется или его сетевой результат неизвестен | повторить то же подтверждение с прежним UUID |
| `accepted` | Sandbox принял запрос | повторная отправка запрещена |
| `failed` | Sandbox однозначно отклонил запрос | повторная отправка запрещена |

При сетевом таймауте нельзя безопасно считать, что заявки нет. Поэтому запись остаётся `submitting`, а повтор `/approve ID CONFIRM` использует тот же `orderId`. Это защищает от создания второй заявки при повторе запроса.

## Защитные ограничения

- отдельный `T_INVEST_TRADING_TOKEN`, который не передаётся MCP и сканеру;
- только `SandboxService/PostSandboxOrder`; live-endpoint в клиенте отсутствует;
- только long, лимитная заявка, `TIME_IN_FORCE_FILL_OR_KILL`, `confirmMarginTrade=false`;
- один заранее рассчитанный размер и цена из карточки;
- повторная проверка возраста кандидата, торгового статуса, bid/ask, спреда, отклонения цены и ликвидности;
- дневной лимит заявок и суммы расчётного риска по московскому календарному дню;
- kill switch включён по умолчанию и сохраняется после рестарта;
- состояния и события записываются в локальный SQLite без токенов и ID брокерского счёта.

`/kill` запрещает только новые отправки. Он не закрывает уже исполненную sandbox-позицию и не отменяет принятую брокером заявку.

## Настройка

Сохраните на сервере два разных токена:

```dotenv
T_INVEST_TOKEN=токен-только-для-чтения
T_INVEST_EXECUTION_MODE=sandbox
T_INVEST_TRADING_TOKEN=отдельный-токен-с-правом-торговли
T_INVEST_SANDBOX_ACCOUNT_ID=
T_INVEST_SANDBOX_INITIAL_BALANCE_RUB=100000
T_INVEST_EXECUTION_MAX_ORDERS_PER_DAY=3
T_INVEST_EXECUTION_MAX_DAILY_RISK_RUB=1000
T_INVEST_EXECUTION_CANDIDATE_MAX_AGE_MINUTES=10
```

После deploy выполните в Telegram:

1. `/execution` — режим `sandbox`, токен задан, kill switch включён.
2. `/execution_arm SANDBOX` — создаётся и один раз пополняется отдельный виртуальный счёт, kill switch выключается.
3. `/orders` — до появления кандидатов список пуст.
4. После карточки — `/approve ID CONFIRM` либо `/reject ID`.
5. `/orders` — проверить итоговый статус.
6. `/kill` — снова запретить отправки.

## Приёмка перед следующим этапом

Песочницу нельзя считать проверенной по одной успешной заявке. До live-разработки нужно накопить достаточную выборку, проверить отсутствие дублей после рестартов и таймаутов, сверить статусы с брокером, а также реализовать автоматические защитные выходы и фактический дневной PnL/лимит убытка.

Контракт полей и idempotency UUID взят из официального [orders.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/orders.proto), sandbox-маршруты — из [sandbox.proto](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/contracts/sandbox.proto). Общие ограничения алгоритмической торговли описаны в [официальной документации T-Invest API](https://github.com/RussianInvestments/investAPI/blob/main/src/docs/algorithmic_trading.md).
